**Context.** `--init deno`, `--init typescript` and `--init javascript` were
three names for nearly the same thing. All three produced the same
`denoMakefileText` Makefile and set `app.deno = true`; they differed only in
whether the version file was `version.ts` or `version.js`. Meanwhile the actual
Deno projects being bootstrapped differ in ways the Makefile has to know about:
a compiled CLI, a browser bundle, bare ES modules, and a web component library
each need different build targets, and only the first needs a `version.ts` at
all.

The old values named the *language*. What the generator needs to know is the
*delivery form*.

**Decision.** Four explicit sub-types, each with its own Makefile template in
`generate_text.ts`:

| Value | `version.*` | Makefile targets |
|---|---|---|
| `deno-cli` | `version.ts` | per-executable `deno compile`, test, clean |
| `deno-bundle` | none | bundle, test, clean |
| `deno-es-module` | none | lint, check, test, clean |
| `deno-webcomponent` | none | manifest, demo, test, clean |

`deno`, `typescript` and `javascript` remain in the switch as deprecated
aliases setting `lang = "deno-cli"`, so existing usage is unchanged and
`lang.startsWith("deno")` still fires for the automatic `deno.json` update.

For `deno-cli`, positional arguments after the `codemeta.json` path are treated
as executable names, so `cmt --init deno-cli codemeta.json cmd1 cmd2` produces
a compile target per executable. With none supplied, the `name` field from
`codemeta.json` is the fallback.

**Rationale.** Naming the delivery form is what lets the Makefile be correct
rather than generic. The previous arrangement generated a CLI-shaped Makefile
for an ES-module project and left the developer to fix it, which is the
copy-and-edit problem CMTools exists to remove
([DR-0001](0001-cmtools-is-a-deno-typescript-cli-and-pandoc.md)).

Executable names as positional arguments rather than a flag: a CLI project can
have several binaries, a repeated flag is more to type than a bare list, and
the position after `codemeta.json` was already where output filenames went, so
the argument shape was familiar.

**Rejected alternatives.**

- *Remove the old values outright.* Cleaner vocabulary, and the old names are
  actively misleading now. Rejected because CMTools is used across nearly every
  work and personal project, so a breaking `--init` change would strand
  documented commands in a lot of READMEs for no functional gain.
- *A separate flag for executable names.* More explicit, but more typing for
  the common single-executable case, which is already covered by the
  `codemeta.json` `name` fallback.
- *Generating `custom-elements.json` for `deno-webcomponent`.* Rejected on
  scope: that file is produced by a manifest analyzer that already exists.
  CMTools generates the Makefile target that calls it, and does not
  reimplement it.

**Consequences.**

- Parsing executable names required care in `cmt.ts`: they had to be captured
  before the general positional-argument loop consumed them as output filenames.
- Four new Makefile templates in `generate_text.ts`, per
  [DR-0002](0002-generated-file-content-lives-in-generate-text-ts.md), all
  requiring hard tabs for recipe lines.
- The alias entries stay in `getMakefileText()`'s map as well as the `--init`
  switch, so the deprecated names have two places they must be kept in step.
